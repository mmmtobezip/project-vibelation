# VIBELATION 화면·기능 정의서

> 2026-10-14 기준으로 논의한 서비스의 화면과 기능을 정리한 문서입니다.
> 이 문서는 **만들고자 하는 화면의 요구사항**이며, 모든 기능이 현재 Mock에 구현되었다는 의미는 아닙니다.

## 1. 서비스 전체 구성

VIBELATION은 개발자·운영자가 현업의 개선 요청을 구체화하고, 기존 시스템의 변경 영향을 검토하며, 팀의 SR 진행 상황을 공유하는 서비스입니다.

| 서비스 | 주요 목적 | 핵심 산출물 |
| --- | --- | --- |
| **1. 요청 작업실** | 자료 정리부터 소스 분석·화면 협의·최종 검토까지 하나의 요청 안에서 진행 | 요구사항 MD 초안, 시스템 적용 Mock, 최종 협의 MD·검토 리포트 |
| **2. 과거 검토 이력** | 확정한 검토 리포트를 모아 검색·조회하고 다음 요청에 재사용 | 검색 가능한 검토 리포트 목록·상세 |
| **3. 팀 진행 현황** | 팀 업무와 SR 진행 상태·완료 일정·표준 공기를 공유하고 확인 | 진행 현황, 일정 경고, 특이 SR 검토 안내 |

### 전체 사용 흐름

```text
현업이 요구사항 전달
  ↓
요청 작업실: 자료 입력 ↔ 레거시 분석 ↔ Mock 화면 협의
  ↓ 최종 협의
협의사항 도출 · 검토 리포트 확정
  ↓
과거 검토 이력에 보관 → 다음 유사 요청의 분석에 활용

협의 완료 내용을 바탕으로 현업이 SR 등록
  ↓ 운영 담당자가 FP 견적 제출
팀 진행 현황에서 SR 일정·표준 공기 점검
  ↓ 필요 시
담당자가 특이 SR 신청과 등록일 조정을 검토
```

요청 작업실은 **SR 등록 이전에도 사용**합니다. 작업실을 만들 때 SR 번호는 필수가 아닙니다.

## 2. 공통 화면 구성과 디자인

### 공통 메뉴

왼쪽 메뉴에서 다음 세 서비스로 이동합니다.

1. 요청 작업실
2. 과거 검토 이력
3. 팀 진행 현황

상단에는 현재 위치, 팀 정보, 사용자와 알림을 표시합니다. 서비스 간 이동 시 같은 요청의 리포트와 연결된 SR을 찾아갈 수 있는 구조를 지향합니다.

### 디자인 방향

- 서비스 이름은 **VIBELATION**입니다.
- MyPOSCO 예시 디자인을 참고한 블루를 주요 색상으로 사용합니다.
- 전체 배경은 밝은 회색, 카드와 사이드바는 흰색으로 구성합니다.
- 본문은 진한 네이비 계열로 표현하고 설명·보조 글자도 충분히 읽히게 합니다.
- 선택 탭·주요 버튼·현재 단계는 블루로 강조합니다.
- 경고는 내용과 아이콘을 함께 표시하여 색상만으로 구분하지 않습니다.
- PC에서는 자료와 화면을 나란히 비교하고, 좁은 화면에서는 세로로 배치합니다.

# 서비스 1. 요청 작업실

## 3. 서비스 목적

여러 소통 창구에서 전달받은 개선 요청을 개발자·운영자가 정리하고, 우리 시스템의 소스를 확인하며, 현업과 화면으로 협의하는 작업 공간입니다.

하나의 요청 작업실 안에 다음 4단계를 제공합니다.

**① 자료 입력 → ② 레거시 분석 → ③ Mock 화면 → ④ 협의사항 도출**

단계는 일방향으로만 진행하지 않습니다. 새로운 자료나 의견이 들어오면 앞 단계로 돌아가 수정·재분석·재생성을 반복합니다. **3단계까지는 협의 확정 전**이며, 4단계에서 검토 결과를 정리하고 담당자가 확정합니다.

## 4. 작업실 공통 영역

| 화면 요소 | 표시·동작 |
| --- | --- |
| 요청 제목 | 개선 요청의 제목을 표시하고 수정 |
| 요청 정보 | 요청 식별자, 담당자, 진행 상태, 요구사항 버전 |
| 4단계 메뉴 | 현재 단계를 강조하고 원하는 단계로 이동 |
| 저장 상태 | 현재 입력 내용의 저장 여부 안내 |
| 새 요청 | 별도 요청 작업을 시작. 기존 작업이 사라질 수 있으면 안내 |
| 재검토 안내 | 요구사항이 바뀌어 이전 분석·Mock이 오래되었으면 표시 |

### 반복 협의의 동작

- 요구사항 추가, 대화 보완, HTML 수정, 협의 의견 변경이 가능합니다.
- 변경된 요구사항에 따라 영향도와 적용 Mock을 다시 검토합니다.
- 이전 결과를 최신 결과처럼 보여주지 않고 **재검토 필요** 상태를 표시합니다.
- 최종 리포트에는 어떤 요구사항·분석·Mock 버전을 기준으로 했는지 남깁니다.
- 목표는 버전별 의견과 결과를 추적하는 것입니다. 현재 Mock은 단계별 모든 과거 버전을 조회하는 기능까지 제공하지는 않습니다.

## 5. 1단계 — 자료 입력

### 목적

현업이 여러 방식으로 전달한 내용을 모아 **현업이 원하는 기능과 화면을 이해하기 위한 입력을 정리**합니다. 기존 화면의 별도 Mock 생성 기능을 이 단계로 옮깁니다.

### 입력 우선순위

1. **대화·텍스트:** Teams 대화 붙여넣기, 회의록, 정리된 메일, 담당자가 작성한 요구사항
2. **HTML:** 현업이 만든 Mock HTML 붙여넣기
3. **PPT:** 요구사항 또는 화면 설명 파일 첨부

Teams 직접 연동이 필수인 것은 아닙니다. 먼저 복사한 대화를 입력하는 방식으로 진행합니다.

### 화면 구성 — 세 영역을 나란히 배치

| 왼쪽: 요구사항 입력 | 가운데: 요구 화면 미리보기 | 오른쪽: 요구사항 MD 초안 |
| --- | --- | --- |
| 자료 유형 탭, 원문·첨부 자료 | 자료에서 추출하거나 생성한 화면 | 정리된 요구사항과 확인 질문 |

### 자료 유형별 기능

| 유형 | 입력과 표현 방식 |
| --- | --- |
| 대화·텍스트 | 원문 입력·편집. 긴 대화는 요약하고 결정사항·질문을 구분. 가능한 경우 발언자와 시간을 유지 |
| HTML | 코드를 붙여넣고 화면으로 렌더링. 코드는 입력·수정 시에만 펼쳐 볼 수 있게 구성 |
| PPT | 슬라이드를 썸네일과 확대 화면으로 보여주고, 각 화면의 설명과 추출 요구사항을 연결 |

### 주요 기능

- 자료 유형 선택 및 원문 입력·첨부
- 협의 중 새 자료 추가
- **화면 구체화:** 입력을 바탕으로 초기 요구 화면과 요구사항 정리 결과 생성
- HTML 미리보기
- 원본과 요약을 함께 확인
- 요구사항 MD 초안 확인·다운로드

### 요구사항 MD 초안의 내용

- 요청 배경과 목적
- 필요한 기능과 기대 동작
- 입력·조회·권한·예외 조건
- 화면 예시
- 이미 합의한 내용과 미확정 사항
- 추가 확인 질문과 원본 자료 출처

**이 단계의 화면은 현업이 원하는 모습입니다.** 실제 시스템의 구조와 제약을 반영한 구현 확정 화면은 아닙니다. MD도 최종 합의 전 초안입니다.

## 6. 2단계 — 레거시 분석

### 목적

1단계 요구를 기준으로 기존 프로젝트 소스를 탐색하여 **어느 자원을 수정하고 검토해야 하는지** 알려줍니다.

분석 대상은 MyPOSCO 가상 레거시의 Front와 Back입니다.

- Front: `mmmtobezip/myposco-demo-front`
- Back: `mmmtobezip/myposco-demo-back`

### 화면 구성

| 영역 | 표시할 내용 |
| --- | --- |
| 분석 대상 정보 | 대상 프로젝트와 분석 기준 소스 버전 |
| 수정·검토 자원 목록 | UI, Logic, API, DB, Permission 등 영향 후보 |
| 자원 상세·변경 비교 | 현재 구조와 변경 방향을 diff와 유사하게 비교 |
| 담당자 검토 영역 | 제약·충돌·미확정 조건·대안·검토 의견 |

### 자원별 상세 정보

- 자원 이름과 파일 경로, 관련 함수·화면 ID
- 현재 동작과 구조
- 요구사항 때문에 변경이 필요한 이유
- 수정 방향과 재사용 가능한 공통 자원
- 연결된 다른 자원과 예상 영향
- 판단 근거와 확인이 필요한 부분
- 잠정 예상 공수와 산정 가정

화면의 전후 비교는 **변경 제안**입니다. 실제 코드가 변경되었다는 뜻으로 표시하지 않습니다.

### 담당자 검토가 필요한 예

현업이 가져온 팝업 화면이 우리 시스템의 공통 팝업 구조에 맞지 않을 수 있습니다.

이때 다음처럼 안내합니다.

- 현재 공통 자원의 구조와 제약은 무엇인지
- 현업 요구와 어느 부분이 맞지 않는지
- 기존 구조에 맞춰 단순화할지
- 별도 화면으로 구성할지
- 공통 자원을 확장할 경우 다른 기능에 어떤 영향을 줄지

Agent는 대안과 근거를 제시하고, **개발자·운영자가 판단하는 휴먼 루프**를 둡니다.

### 주요 동작

- 영향도 분석 실행·갱신
- 자원을 선택하여 상세 내용 확인
- 변경 방향·재사용 후보 확인
- 검토 의견 작성
- 추가 협의가 필요하면 자료 입력으로 돌아가기
- 분석 결과를 기반으로 3단계 Mock 생성

## 7. 3단계 — Mock 화면

### 목적

2단계의 분석 결과와 담당자 의견을 반영해 **우리 시스템 기준의 적용 제안 화면**을 만들고, 이를 보며 현업과 협의합니다.

기존에 시스템 화면을 캡처하고 PPT에서 버튼 등을 편집해 설명하던 작업을 화면 비교로 대신하는 취지입니다.

### 1단계 화면과의 차이

| 구분 | 1단계 요구 화면 | 3단계 시스템 적용 Mock |
| --- | --- | --- |
| 기준 | 현업의 원하는 모습 | 기존 시스템 자원·제약과 요구사항 |
| 목적 | 요구 이해 | 구현 방향을 화면으로 협의 |
| 상태 | 초기 초안 | 시스템을 반영한 제안, 아직 미확정 |

### 화면 구성

- **현재 시스템 / 적용 제안** 전환 또는 나란히 비교
- 필요한 경우 1단계의 현업 원본 화면 참조
- 변경 영역과 관련 요구사항 설명
- 협의 노트·수정 요청 영역
- 자료 추가·재분석·Mock 재생성 이동

### 주요 기능

- 시스템 분석 결과를 반영한 Mock 생성
- 기존 공통 버튼·모달·레이아웃을 고려한 화면 구성
- 버튼 위치, 조건별 노출, 입력·확인 절차 등을 화면으로 확인
- 협의 의견 작성·보완
- 요구 변경 시 1단계나 2단계로 돌아가 반복

여기서 바로 협의를 확정하지 않습니다. 대화와 수정을 충분히 반복한 뒤 4단계에서 결과를 정리합니다.

## 8. 4단계 — 협의사항 도출

### 목적

1~3단계에서 반복 검토한 결론을 최종 협의 내용과 검토 리포트로 남깁니다. 다른 운영자가 오거나 유사 요청이 들어와도 당시 판단을 이해할 수 있어야 합니다.

### 화면 구성 — 검토 리포트

| 탭 | 주요 내용 |
| --- | --- |
| 요약 | 요청 배경, 핵심 결론, 합의 범위, 주요 검토 지표 |
| 영향도 분석 | 관련 시스템 영역과 영향 관계, 판단 근거 |
| 수정 자원 | 수정·신규·재사용 후보와 파일·기능별 변경 방향 |
| 유사 사례 | 참고한 과거 검토, 공통점·차이점 |
| 공수 | 작업별 예상 공수, 근거·가정·미확정 조건 |
| 구현 방안 | 적용 순서, 재사용 방식, 예외 처리 방향 |
| 검토 의견 | 담당자 의견, 추가 확인 사항, 제외 범위 |

### 주요 기능

- 최종 협의 내용을 리포트 형태로 확인
- 수정 범위와 제외 범위 확인
- 담당자 검토 체크 및 확정
- **최종 협의 MD 다운로드**
- **검토 리포트 등록** → 과거 검토 이력으로 연결

최종 MD는 Copilot/GPT/Codex에 전달할 수 있도록 기능·수정 대상·제약·수용 기준을 정리합니다.

1단계의 MD는 요구 이해를 위한 초안이고, 4단계의 MD는 **반복 협의를 반영한 최종 결과**입니다.

예상 공수는 공식 FP 견적 MM과 별개입니다. 검토 리포트를 저장한 시점에 실제 수행 결과가 이미 존재한다고 가정하지 않습니다.

# 서비스 2. 과거 검토 이력

## 9. 서비스 목적

요청 작업실에서 확정한 **4단계 검토 리포트들을 모아두는 서비스**입니다. 검토 결과를 팀의 자산으로 남기고 유사 요청의 분석 근거로 재사용합니다.

## 10. 목록 화면

### 표시 정보

- 리포트 제목
- 대상 시스템
- 주요 검토 내용 요약
- 작성자·확정일·버전
- 검토 상태
- 연결된 SR 정보가 있다면 표시

### 주요 기능

- **제목 키워드 검색**
- 리포트 목록에서 상세 화면으로 이동
- 리포트가 없거나 검색 결과가 없을 때 안내

자료가 누적되었을 때 제목으로 원하는 검토 결과를 쉽게 찾는 것이 기본 요구입니다. 시스템·기간·담당자 필터는 확장할 수 있지만 제목 검색을 우선합니다.

## 11. 상세 화면

- 작업실 4단계에서 확정한 리포트를 당시 내용으로 표시합니다.
- 요약·영향도·수정 자원·유사 사례·공수·구현 방안·검토 의견을 확인합니다.
- 기준 요구사항 버전과 검토 시점을 확인합니다.
- 리포트를 Markdown으로 다운로드합니다.
- 관련 요청이나 SR이 연결되어 있으면 찾아갈 수 있도록 합니다.

### 과거 결과를 활용하는 방식

- 새로운 요청의 분석에서 과거 리포트를 유사 사례로 찾아 참고합니다.
- 어떤 조건이 같고 다른지 함께 보여줍니다.
- 과거 예상 공수를 실제 수행 공수처럼 사용하지 않습니다.
- 재검토할 때 당시 리포트를 덮어쓰지 않고 새로운 결과를 남기는 방향으로 관리합니다.

# 서비스 3. 팀 진행 현황

## 12. 서비스 목적

팀원들이 현재 유지보수 업무와 SR 처리 상황을 공유하고, 완료일 임박·지연 및 표준 공기 문제를 빠르게 확인하는 공간입니다.

크게 **팀의 진행 상태**, **SR 일정·표준 공기 경고**, **활동 이력**을 다룹니다.

## 13. SR 업무의 실제 순서

1. 현업 요구 제안
2. 개발자·운영자 영향도 검토
3. 회의·협의 완료
4. 현업이 협의된 내용과 완료 요청일로 SR 등록
5. 운영 담당자가 FP 견적서 제출
6. FP 견적 MM으로 표준 처리 근무일 계산
7. 등록 일정이 표준 공기를 넘으면 특이 SR 검토

공식 MM은 운영 담당자가 자원을 분석하고 화면 ID·기능 단위로 산정합니다. **FP 견적서 작성·업로드 자동화는 이번 범위에서 제외**하고, 제공된 데이터의 MM을 사용합니다.

## 14. 진행 현황 화면

### 상단 요약

- 진행 중 업무 건수
- 완료일 임박 건수
- 완료일 초과 건수
- 표준 공기 검토 필요 건수
- 전체 등록 현황

요약 항목을 선택하면 관련 목록을 볼 수 있게 합니다.

### 목록의 검색·필터

- SR 번호·제목 검색
- 담당자별 조회
- 전체 / 진행중 / 완료일 임박 / 완료일 초과 / 표준 공기 검토

### SR 목록 표시 정보

| 항목 | 설명 |
| --- | --- |
| SR 번호·제목 | 어떤 개선 업무인지 식별 |
| 분류 | SR / RR / ITSM |
| 처리자 | 담당 팀원 |
| 원본 상태 | 진행중 / 완료 / 취소 / 지연 / 임박 / 지연(리드타임) |
| 처리단계 | 접수 / 작업계획수립 / 작업수행 / 작업결과확인 / 테스트결과확인 |
| 요청처리일 | SR 등록일 |
| 요청완료일 | 현업과 협의한 완료 요청 날짜 |
| FP 견적 MM | 표준 처리일 계산에 사용하는 공식 견적 |
| 표준 처리일수 | MM 구간표로 계산한 허용 근무일수 |
| 표준 기한 | 등록일부터 표준 근무일을 센 날짜 |
| 검토 알림 | 완료일 위험과 표준 공기 문제를 구분하여 표시 |

현재 제공된 40건을 기준으로 진행하며, 데이터에 없는 세부 유형 선택 화면은 추가하지 않습니다. 원본 값은 보존하고 계산한 경고와 구분합니다.

## 15. 표준 공기 판정

### 확정한 기본 규칙

- **워킹데이 기준이며 주말·공휴일을 제외**합니다.
- 요청처리일을 SR 등록일로 봅니다.
- FP MM을 표준표의 근무일수로 매핑합니다.
- 등록일 기준 표준 기한보다 요청완료일이 늦으면 표준 공기 초과로 안내합니다.

| FP MM 구간 | 표준 처리 근무일 |
| --- | ---: |
| 0.0 이상 ~ 0.3 미만 | 8일 |
| 0.3 이상 ~ 0.6 미만 | 11일 |
| 0.6 이상 ~ 1.0 미만 | 15일 |
| 1.0 이상 ~ 1.5 미만 | 22일 |
| 1.5 이상 ~ 2.5 미만 | 26일 |
| 2.5 이상 ~ 3.5 미만 | 40일 |
| 3.5 이상 ~ 5.0 미만 | 50일 |

```text
표준 기한 = 요청처리일 + MM에 따른 표준 근무일수
표준 공기 초과 = 요청완료일 > 표준 기한
등록일 조정 제안 = 요청완료일에서 표준 근무일수를 역산한 날짜
```

예를 들어 0.5 MM이면 11근무일입니다. 등록일부터 계산한 11근무일 기한보다 요청완료일이 늦으면, 요청완료일을 기준으로 적정 등록일을 역산해 담당자에게 제안합니다.

### 서로 다른 알림의 구분

| 알림 | 의미 |
| --- | --- |
| 완료일 임박 | 약속한 완료일이 가까운데 아직 미완료 |
| 완료일 초과 | 약속한 완료일이 지났는데 아직 미완료 |
| 표준 공기 초과 | SR을 일찍 등록했거나 일정이 길어 MM 대비 허용 처리기간을 넘음 |
| 판정 보류 | MM·유형·달력 등 계산 기준을 확인해야 함 |

표준 공기 경고는 요청완료일이 아직 오기 전에도 발생할 수 있습니다. 실제 개발 지연과 같은 의미로 취급하지 않습니다.

## 16. SR 상세·특이 SR 검토 화면

목록에서 SR을 선택하면 계산 근거와 조치 제안을 확인합니다.

### 상세 정보

- SR 번호·제목·담당자·원본 상태·처리단계
- 원본 등록일과 요청완료일
- FP 견적 MM·표준 처리일수
- 적용한 계산 기준과 표준 기한
- 등록 일정의 근무일수와 표준 기한 초과 여부
- 요청완료일에서 역산한 등록일 조정 제안

### 특이 SR 안내

표준 공기를 초과하면 **특이 SR 검토 필요**를 표시합니다.

- 조정이 필요한 이유와 계산 근거를 설명합니다.
- 등록일 조정 제안과 지연 처리 해제 요청 메일 초안을 제공합니다.
- 담당자가 등록 경위와 실제 작업 일정을 확인하고 사유를 작성합니다.
- 사람의 검토 후 실제 SR 시스템에서 처리합니다.

**등록일·상태를 자동 변경하거나 특이 SR을 자동 신청하지 않습니다.** 원본 정보와 제안 정보를 구분해 보여줍니다.

### 메일 초안 내용

- SR 번호와 제목
- 공식 MM과 표준 처리일수
- 원본 등록일·요청완료일
- 조정 제안일
- 담당자가 보완할 사유
- 특이 SR 및 지연 처리 해제 검토 요청

## 17. 팀 활동 이력과 Teams 알림

### 팀 활동 이력

팀원이 진행한 주요 작업을 시간 순으로 확인하는 화면입니다.

- 요구 자료 접수·추가
- 분석 수행·검토 의견 추가
- Mock 생성·협의
- 리포트 확정·등록
- 연결된 SR의 진행 상태 변경

활동에는 요청 제목, 담당자, 작업 내용, 시점을 표시하고 관련 작업실·리포트·SR로 연결합니다.

### 알림

- 팀 진행 현황 안에서 임박·초과·표준 공기 검토 대상 안내
- 향후 Teams 메시지로 같은 경고를 전달하는 기능 검토
- 실제 발송은 수신 채널·시점·중복 방지·검토 방식을 정한 뒤 연결

팀 활동 타임라인과 Teams 실제 발송은 현재 Mock에 연결되어 있지 않습니다.

## 18. SR 화면에서 주의할 데이터 조건

- 제공 파일에는 실제 완료일이 없습니다. 완료 상태의 건은 등록 일정의 표준 공기 초과 여부만 확인할 수 있으며 실제 지연 완료라고 확정하지 않습니다.
- SR 번호가 중복된 행이 있으므로 목록에서 다른 건을 덮어쓰지 않아야 합니다.
- 별도의 일상 SR 세부 유형은 현재 입력 데이터에 없습니다. 제목만 보고 유형을 자동 확정하지 않습니다.
- 현재 Mock은 SR에 유지보수 MM 표를 적용하고 RR/ITSM은 적용 기준 확인 전 판정을 보류합니다.
- 5.0 MM 이상이나 유효하지 않은 MM은 임의로 표준일을 만들지 않습니다.

## 19. 현재 Mock과 추후 연결 기능

| 구분 | 현재 확인할 수 있는 화면·동작 | 아직 연결하지 않은 기능 |
| --- | --- | --- |
| 요청 작업실 | 4단계 이동, 텍스트 입력, HTML 미리보기, 샘플 분석·Mock·MD, 협의 노트, 재검토 안내, 리포트 등록 | 실제 AI 분석·생성, PPT 슬라이드 추출, 모든 단계의 과거 버전 조회 |
| 과거 검토 이력 | 로컬 리포트 목록·제목 검색·상세 탭·MD 다운로드 | 팀 공용 저장, 의미 기반 유사 사례 검색 |
| 팀 진행 현황 | SR 40건 검색·필터, 근무일 계산, 표준 공기 경고, 조정 제안·메일 초안 | SR 시스템 연동, FP 파일 업로드, 활동 타임라인, Teams/메일 실제 발송 |

현재 화면의 분석·공수·요구사항 추출은 고정 시나리오로 보여주는 Mock입니다. 실제 AI 처리 결과가 아닙니다. 브라우저에 저장한 작업·리포트는 팀원에게 자동 공유되지 않습니다.

## 20. 세부 확정이 필요한 화면 규칙

아래는 사용자에게 확정받은 규칙과 혼동하지 않도록 구분합니다.

- **등록일 산입:** 현재 Mock은 등록일 다음 근무일부터 계산합니다. 회사 실제 사례와 대조가 필요합니다.
- **임박 기준:** 현재 Mock은 기준일 이후 2근무일 이내입니다. 최종 운영 기준은 미확정입니다.
- **시연 기준일:** 현재는 2026-10-14로 고정합니다. 운영 시 실제 날짜 기준으로 전환해야 합니다.
- **공휴일:** 현재는 2026년 한국 공휴일 목록을 사용합니다. 회사 휴무·다른 연도·임시공휴일의 공급 방식은 후속 결정입니다.
- **비근무일 완료요청:** 완료요청일이 휴일이면 등록일 역산을 어떻게 보정할지 확인해야 합니다.
- **분류별 표준표:** RR/ITSM 및 일상 SR의 상세 적용 방식은 추가 확인이 필요합니다.

## 21. 팀원에게 공유할 핵심 요약

1. **요청 작업실은 네 단계가 하나의 서비스다.** 입력·분석·화면 협의를 반복한 뒤 최종 리포트를 남긴다.
2. **1단계와 3단계의 Mock은 목적이 다르다.** 1단계는 현업의 원하는 모습, 3단계는 우리 시스템에 맞춘 적용 제안이다.
3. **과거 검토 이력은 최종 리포트의 보관·검색 서비스다.** 다음 요청의 판단 근거로 재사용한다.
4. **팀 진행 현황은 SR 등록 이후의 팀 업무와 일정 위험을 관리한다.** 공식 FP MM으로 표준 기한을 계산한다.
5. **완료일 지연과 표준 공기 초과는 다르다.** 표준 공기 문제는 등록일 조정을 제안하고 사람이 검토한다.
