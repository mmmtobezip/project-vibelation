- 작성일: 2026-10-14 (한국 시간)
- 목표: 2026-10-23 AX 해커톤
- 상태: 사용자와 합의한 제품 방향 및 현재 인터랙티브 Mock 기준. 미확정 항목은 아래에 별도 명시한다.
- 용도: 팀원이 각자 Codex에 이 파일을 첨부하고 담당 범위를 지정하여 공통 맥락으로 작업한다.

## 1. 제품 정의와 핵심 사용자

VIBELATION은 현업의 개선 요청을 자료와 화면으로 구체화하고, 기존 시스템 소스를 근거로 변경 후보를 검토하며, 화면 중심의 협의를 거쳐 검토 리포트를 남기는 서비스다. 축적한 리포트는 다음 요청의 분석 근거로 재사용한다. SR 등록 이후에는 팀의 진행 상황과 표준 공기 위험을 확인한다.

핵심 사용자는 개선 요청을 접수·분석·협의하는 **개발자/운영자**다. 현업은 요구 자료 제공과 화면 협의에 참여한다. 현업이 분석 대상 소스에 직접 접근하는 것을 전제하지 않는다.

핵심 메시지: **같이 보고, 근거로 판단하고, 결과를 다음 판단에 다시 쓴다.**

## 3. 업무 흐름과 세 서비스

```text
현업 요구 제안 (대화·회의록·메일·HTML·PPT)
  ↓
서비스 1: 요청 작업실
  자료 입력 ↔ 레거시 분석 ↔ 시스템 기준 Mock 협의
  ↓ 담당자 최종 검토
  협의사항·검토 리포트 확정
  ↓
서비스 2: 과거 검토 이력에 보관 → 다음 요청에서 재사용
  ↓ 현업이 협의 완료 내용으로 SR 요청·등록
운영 담당자가 FP 견적 제출
  ↓
서비스 3: 팀 진행 현황에서 SR 일정·표준 공기 점검
```

SR 번호는 작업실 생성 시 필수가 아니다. 리포트와 SR의 연결은 SR 등록 후 가능해야 한다. FP 견적서는 운영 담당자가 화면 ID와 기능별 영향도를 검토하여 작성한다. Agent의 잠정 공수와 공식 FP 견적은 구분한다.

## 4. 서비스 1 — 요청 작업실

하나의 요청 안에 다음 4단계를 제공한다. 강제 일방향 마법사가 아니라 협의하며 반복하는 작업 공간이다.

### 4.1 자료 입력

목적: 여러 소통 창구의 원본을 운영자/개발자가 모아 현업이 원하는 동작을 정리한다.

입력 우선순위:

1. Teams 대화 붙여넣기 / 회의록 / 메일 / 담당자 정리 텍스트
2. Mock HTML 붙여넣기
3. PPT 파일

화면의 기본 세 영역:

| 영역 | 내용 |
| --- | --- |
| 요구사항 입력 | 원본 자료와 출처, 텍스트 편집·자료 추가 |
| 요구 화면 미리보기 | 추출하거나 생성한 초기 화면, HTML 렌더링 |
| 요구사항 MD 초안 | 배경·기능·동작 조건·추가 확인 질문·출처 |

- 긴 대화는 원문을 보존하면서 요약·결정·미확정 사항을 구분하는 것이 목표다.
- HTML 코드는 입력 시 필요할 때만 노출하고 기본 결과는 렌더링된 화면으로 제시한다.
- 기존 앱의 별도 Mock 생성 기능을 이 단계로 이동한다.
- PPT는 최종적으로 슬라이드 이미지·텍스트·추출 요구사항을 연결해 표현한다. 현재는 파일 선택/이름 확인만 구현했다.
- 여기의 MD는 **현업 요구 이해를 위한 초안**이다. 최종 협의·구현 가능성 확정을 의미하지 않는다.

### 4.2 레거시 분석

목적: 1단계 요구가 들어오면 우리 프로젝트의 어느 자원을 변경·검토해야 하는지 근거를 제공한다.

각 변경 후보에 필요한 정보:

- 파일 경로, 심벌/함수/화면 ID, 가능하면 근거 줄 번호
- 현재 구조와 동작
- 요구사항과 연결된 변경 이유
- 변경 방향 및 재사용 가능한 자원
- 영향 관계(UI/Logic/API/DB/Permission 등)
- 확인된 사실 / 추론 / 미확인 조건의 구분
- 작업별 잠정 공수와 가정
- 담당자가 결정해야 할 제약·대안

PR diff처럼 전후를 비교하되 **아직 적용하지 않은 변경 제안**임을 표시한다. 분석 대상 소스 수정·자동 PR 생성은 이번 Mock의 범위가 아니다.

휴먼 루프 예: 현업 HTML이 다단계 입력 팝업을 요구하지만 기존 공통 팝업은 단순 확인 구조라면, 기존 구조 안에서 단순화 / 별도 화면 / 공통 팝업 확장 등 대안과 영향을 제시하고 담당자가 판단한다. 실제 소스 확인 없이 해당 제약이 존재한다고 단정하지 않는다.

### 4.3 Mock 화면

목적: 분석된 시스템 구조와 담당자 의견을 반영한 화면으로 현업과 협의한다. **아직 최종 확정 전이다.**

- 1단계: 현업이 원하는 모습 이해용 화면.
- 3단계: 우리 시스템 자원·제약을 반영한 적용 제안 화면.
- 현재 시스템 / 적용 제안을 비교하고 현업 원본도 참조할 수 있게 한다.
- 공통 버튼·모달·레이아웃 재사용, 조건·권한·오류 안내를 표현한다.
- 협의 노트를 남기고 자료 추가·요구 수정·영향 재분석으로 돌아갈 수 있다.
- 생성된 HTML은 안전한 미리보기 경계를 유지한다.

### 4.4 협의사항 도출·검토 리포트

목적: 반복 협의의 최종 결론을 구조화해 남긴다.

리포트 탭: **요약 / 영향도 분석 / 수정 자원 / 유사 사례 / 공수 / 구현 방안 / 검토 의견**.

필수 포함 정보:

- 요청 배경, 최종 합의 기능, 제외 범위
- 기준 요구사항 버전·소스 버전·Mock 버전
- 영향 후보와 근거, 수정/재사용 자원
- 유사 사례의 공통점·차이점과 출처
- 작업 분해·잠정 공수·가정·미확정 사항
- 구현 방향과 수용 기준
- 담당자 검토 결과

요구사항 MD 초안과 달리 최종 MD는 개발 도구(Copilot/GPT/Codex)에 전달할 수 있는 수정 범위·제약·수용 기준을 담는다. 현재 다운로드 형식은 Markdown이다. PDF는 미구현이다.

현재 등록 조건: 최신 요구 버전의 자료 구체화·영향 분석·시스템 Mock 완료 + 두 담당자 확인 체크. 등록 시 당시 내용의 스냅샷을 보관한다.

### 4.5 반복과 버전 관리

- 요구 원문·HTML·제목·협의 내용이 바뀌면 요구사항 버전을 올린다.
- 확인 체크를 해제하고 이전 분석·Mock을 재검토 대상으로 표시한다.
- 오래된 결과로 리포트 확정을 진행하지 않는다.
- 목표 설계는 버전별 결과·의견을 보존한다. **현재 Mock은 활성 작업 하나의 최신 상태와 생성 버전 번호만 저장하며, 단계별 과거 스냅샷 전체 보존은 미구현이다.**
- 리포트 등록 스냅샷은 수정된 활성 작업과 구분한다.

## 5. 서비스 2 — 과거 검토 이력

- 확정 리포트 목록·제목 키워드 검색·상세 조회·Markdown 다운로드.
- 제목, 작성자, 확정일, 기준 버전, 대상 시스템을 표시한다.
- 재검토는 새 버전으로 남기고 당시 결론을 덮어쓰지 않는 것이 목표다.
- 다음 요청에서 유사 리포트를 검색·인용한다. 원문 출처와 현재 요청과의 차이를 제시한다.
- 검토 리포트는 개발 전 판단이다. 실제 완료 범위·실제 공수는 후속 데이터이며 추정치를 실적으로 취급하지 않는다.
- 현재 Mock의 검색은 로컬 목록 필터이며 의미 검색/RAG는 미연결이다.

## 6. 서비스 3 — 팀 진행 현황

### 6.1 데이터와 현재 범위

사용자 제공 `SR 데이터 표준 공기일 가이드.xlsx`의 첫 시트 40건을 이용한다. 두 번째 시트는 표준 처리일 기준이다. SR 시스템 직접 연동과 FP 견적서 파싱/업로드는 후속 과제다.

현재 필드:

| 필드 | 의미 |
| --- | --- |
| SR NO | 외부 SR 번호. 제공 자료에 중복이 있어 단독 내부 PK로 사용하지 않음 |
| 분류 | SR / RR / ITSM |
| 제목·사유·주요 변경내용 | 요구와 변경 설명. Mock 목록 데이터는 주요 조회 필드만 추출한 상태 |
| 제기자·처리자 | 요청자와 담당자. 현재 화면은 처리자 중심 |
| 상태 | 진행중 / 완료 / 취소 / 지연 / 임박 / 지연(리드타임) |
| 처리단계 | 접수 / 작업계획수립 / 작업수행 / 작업결과확인 / 테스트결과확인 |
| 처리일 | 요청처리일 = SR 등록일 |
| 요청완료일 | 현업과 협의한 완료 요청 날짜. 실제 완료일과 다름 |
| FP견적 | 이미 산출된 공식 MM 값 |
| 표준공기일 | 원본은 비어 있음. MM과 표준표를 이용해 계산 |

원본에 처리단계 `완료` 등 열거값과 다른 값이 있으면 원본을 보존하고 정규화 여부를 따로 검토한다. 원본 상태와 앱이 계산한 경고를 구분해 저장·표시한다.

### 6.2 MM별 표준 처리 근무일 — 확인된 기준

| MM 구간 | 표준 근무일 |
| --- | ---: |
| 0.0 이상 ~ 0.3 미만 | 8 |
| 0.3 이상 ~ 0.6 미만 | 11 |
| 0.6 이상 ~ 1.0 미만 | 15 |
| 1.0 이상 ~ 1.5 미만 | 22 |
| 1.5 이상 ~ 2.5 미만 | 26 |
| 2.5 이상 ~ 3.5 미만 | 40 |
| 3.5 이상 ~ 5.0 미만 | 50 |

- 하한 포함, 상한 제외. 0.6 MM은 15일, 1.0 MM은 22일이다.
- 5.0 MM 이상·음수·누락/잘못된 MM은 임의 추정하지 않고 판정 보류한다.
- 일상 SR 가이드에는 즉시(DML/데이터 추출/문의) 2일, 타 시스템 연계(즉시 외) 5일, AI 모델 개발 및 이행 22일도 존재한다.
- 사용자는 현재 데이터 기준으로 진행하기를 원했다. 별도 일상 SR 세부 유형 선택 UI는 이번 범위에서 제외한다.
- **현재는 SR 분류에 유지보수 MM 표를 적용한다. RR/ITSM은 기준 미확인으로 보류한다.** 제목의 키워드만으로 일상 SR 유형을 자동 확정하지 않는다.

### 6.3 표준 기한 계산 — 사용자 확인 규칙

근무일은 주말·공휴일을 제외한다.

```text
N = FP MM 구간에 해당하는 표준 처리 근무일
표준 기한 = 요청처리일로부터 N 근무일을 더한 날짜
표준 공기 초과 = 요청완료일 > 표준 기한
등록일 조정 제안 = 요청완료일에서 N 근무일을 역산한 날짜
```

- 현재 Mock은 **등록일은 제외하고 다음 근무일부터 1일**로 센다. 등록 당일 산입 여부는 회사 계산 사례와 대조해 확정해야 한다.
- 표준 기한과 요청완료일이 같으면 기준 이내다.
- 약속한 완료일이 아직 오지 않았어도 등록 일정이 표준 기간을 초과하면 경고한다.
- 등록일을 조정해야 할 수 있다는 **안내/제안만 제공**한다. 자동으로 특이 SR 처리하거나 원본 등록일·상태를 변경하지 않는다.
- 담당자는 등록 경위·실제 일정·날짜를 확인하고 특이 SR 및 지연 처리 해제 요청을 검토한다.
- 요청완료일이 비근무일일 때의 역산·보정은 회사 규칙 미확정이므로 제안 날짜를 추가 확인해야 한다.

현 구현은 코드에 나열한 2026년 한국 공휴일·대체공휴일을 사용한다. 회사 휴무일·추가 임시공휴일·다른 연도의 달력은 지원되지 않는다. 실서비스에서는 버전이 관리되는 업무 달력을 연결해야 한다.

### 6.4 서로 다른 경고를 혼동하지 않기

| 경고 | 의미 |
| --- | --- |
| 완료일 임박 | 미완료이며 요청완료일이 기준일 이후 2근무일 이내 (현재 Mock의 임시 기준) |
| 완료일 초과 | 미완료이며 요청완료일이 기준일보다 과거 |
| 표준 공기 초과 | 요청완료일이 MM 기준 표준 기한보다 늦음 |
| 기준 확인 필요 | 유형·MM·달력 등의 판정 근거 부족 |

- 현재 시연 기준일은 **2026-10-14**로 고정하고 화면에도 표시한다. 실서비스의 오늘 날짜와 혼동하지 않는다.
- 완료 건의 표준 경고는 **등록 일정에 대한 경고**다. 실제 완료일이 없으므로 실제 지연 완료 여부를 단정하지 않는다.
- 임박·완료일 초과는 현재 Mock에서 상태가 `진행중`인 건에만 적용한다. 모든 실제 상태를 포괄하는 미완료 판정은 후속 정규화 작업이다.
- 목록의 제목/SR 번호 검색, 담당자 필터, 진행중·임박·초과·표준 공기 필터를 제공한다.

### 6.5 특이 SR 상세와 알림

상세: 원본 등록일·요청완료일·MM·표준 처리일·표준 기한·등록 일정 근무일·조정 제안일·계산 가정.

메일 초안: SR 번호/제목, FP MM, 표준 일수, 원본 일정, 조정 제안일, 담당자가 작성할 등록 경위, 특이 SR 및 지연 처리 해제 검토 요청.

현재는 화면 경고와 메일 초안만 제공한다. 메일/Teams 실제 발송은 미연결이며 수신 대상·권한·중복 방지·발송 시점을 별도 설계해야 한다. **팀 공유 문서를 작성하거나 알림 UI를 만드는 일은 실제 메시지 발송 권한을 의미하지 않는다.**

팀 활동 타임라인(누가 자료 추가·분석·확정했는지)은 제품 목표에 포함되지만 현재 Mock에서는 별도 구현하지 않았다.

## 7. Agent와 규칙 엔진의 책임 — 권장 구현안

| 영역 | 담당 |
| --- | --- |
| 대화 정리·질문·요구사항 MD | LLM/Agent + 원문 출처 |
| 코드 탐색·영향 후보·변경안 | 검색 도구 + Agent + 파일 근거 |
| 시스템 기준 Mock | Agent + 기존 UI 자원 + 안전한 렌더링 |
| 최종 검토 리포트 | 버전이 일치하는 분석 결과와 담당자 합의 |
| 유사 사례 | 저장된 리포트/Case 검색, 출처와 차이점 |
| MM 구간·근무일·초과 판정 | 결정적 규칙 엔진. LLM이 날짜나 구간을 임의 산출하지 않음 |
| 합의·공식 견적·특이 SR 판단 | 인간 담당자 |

권장 도구 경계: `search_sources`, `read_source`, `find_related_resources`, `search_cases`, `generate_preview`, `calculate_sr_deadline`. 실제 함수명과 API는 팀 합의 후 확정한다. 현재 이 도구들이 연결되어 있다는 뜻은 아니다.

분석 응답에는 요구사항 버전·소스 식별자·근거 위치를 포함하고 모르는 사항은 명시한다. “모든 영향 파악”, “구현 가능 확정”, “공수 보장”을 자동으로 선언하지 않는다.

## 8. 권장 데이터 모델과 연결

아래는 신규 백엔드/API 설계 시 출발점이며 구현 완료된 스키마가 아니다.

| 엔터티 | 주요 필드 |
| --- | --- |
| Request | id, title, systemId, ownerId, currentVersion |
| SourceMaterial | id, requestId, type, originalName, content/storageRef, sourceMetadata |
| RequirementVersion | requestId, version, requirements, questions, scope, exclusions, acceptanceCriteria |
| AnalysisRun | id, requirementVersion, sourceSnapshotId, status, resources, evidence, estimates, reviewItems |
| MockRevision | id, requirementVersion, analysisRunId, htmlRef, notes |
| Agreement | id, requirementVersion, analysisRunId, mockRevisionId, decisions, reviewer, reviewedAt |
| ReviewReport | id, immutableSnapshot, markdown, author, registeredAt |
| SRRecord | internalId, externalSrNo, sourceRow, category, originalStatus, stage, owner, registeredDate, requestedDueDate, fpMM |
| SRCalculation | srId, rulesVersion, calendarVersion, referenceDate, standardDays, deadline, proposedRegisteredDate, warnings |
| ActivityEvent | entityId, actor, type, timestamp, relatedVersion |

FP MM, Agent 예상 MD, 예상 일정, 실제 수행 공수는 서로 다른 필드다. MM↔MD를 임의 환산하지 않는다. 보고서 스냅샷과 과거 분석을 수정 가능한 최신 작업 상태와 분리한다.

## 9. UI 디자인 기준

- 서비스명은 **VIBELATION**을 사용한다. 참고 이미지의 SteelFlow는 제품명으로 사용하지 않는다.
- MyPOSCO 참고 디자인의 블루, 밝은 배경, 흰 카드, 탭, 정돈된 표를 따른다.
- 사용자 피드백으로 다크 배경을 제거했다. **사이드바도 흰색**, 본문은 진한 네이비, 설명은 충분히 진한 색으로 표시한다.
- 운영체제 다크 모드에서도 `color-scheme: light`로 읽기 쉬운 라이트 UI를 유지한다.
- 현재 강조색은 `#2164d8`, 페이지 배경은 `#f3f6fb`다.
- 장식보다 정보 위계·출처·경고 의미를 우선한다. 표준 공기 위험과 실제 완료일 지연을 색상 하나로 합치지 않는다.
- 데스크톱은 자료/화면/MD 3열, 작은 화면은 세로 배치한다.
- 실제 MyPOSCO 로고·이미지의 무단 복제 없이 제공된 예시와 가상 레거시 UI를 참고한다.
